# 站点 GEO/SEO 优化实施方案（详细版）

> 仅此一种生成模式：**详细多篇版**。快速版（19 章平铺确定性组装）已废弃移除，任何站点方案一律按本规范分篇生成 `-geo-solution-detailed.md`。

## 执行流程

1. **确认目标站点**：从用户输入提取站点（域名或 site key）。方案基于诊断报告，若该站点还没有诊断报告，先走 site-diagnosis 流程（diagnose_site + report_write）生成报告，再回来生成方案。
2. **读取规范**：Read `references/plan-template.md`（v2 详细多篇版），按其篇章结构、章节子节与"详细粒度硬性要求"逐章撰写。
3. **渲染判定**：取自诊断 §5.5——JS 空壳 → 上篇走"技术重建方案"（含设计工作流）；SSR/可读 → 上篇走"技术修复与加固方案"（维持现有栈）。判定依据原文写入 §1.2。
4. **生成方案**：按规范撰写多篇详细方案，落盘 `<SITES_ROOT>/<site>/data/plans/<YYYYMMDD>-<site>-geo-solution-detailed.md`。
5. **核对输出**：五篇结构完整（上篇/中篇/价值桥接/下篇/附录）、诊断 P0/P1/P2 每条四段式展开、关键词矩阵六子类有具体词、人力工作量矩阵合计自洽（修复路线约 24–30 人日 / 重建路线约 32–40 人日）。
6. **汇报**：向用户概括——方案落盘路径、篇章结构、基于诊断的核心问题映射（P0 清单）、人力工作量总计（人日）、以及方案中标注"待验证/待补充"的项（这些需要人工核实后再落地）。

## 方案基本原则

- 方案是**诊断报告的落地实施计划**：每一项结论都来自诊断证据；诊断报告里没有的证据，方案输出"待验证/待补充"占位，绝不编造数值（如 sitemap 规模、500 数量、报价）。
- 渲染方式判定自动完成：诊断判定为 JS 空壳 → 上篇走"重建 SSR"路线（含设计师工作量）；判定为 SSR/可读 → 上篇走"现有栈修复加固"路线（不用人工指定）。
- 报价默认不含金额：下篇第十七章**必须**给出人力工作量矩阵（人日），金额仅在用户明确要求报价时给出（quote:true 口径，单价可覆盖）。
- 篇章结构、章节子节与默认口径以 `references/plan-template.md`（v2 详细多篇版）为准；与模型直觉冲突时以文件为准。

## 与 site-diagnosis 的衔接

- **先诊断、后方案**：方案输入是站点 `data/reports/` 下最新的诊断报告。诊断缺失 → 先调用 site-diagnosis 流程。
- 诊断报告的 14 节结构与方案的五篇 20 章一一映射（健康度总评→预期目标表、问题汇总→方案问题清单四段式、CITE 评分→GEO 专项、规模盘点→sitemap 章节等），映射关系见 `references/plan-template.md`。
