# AI 可见性监测

## 用途

观测品牌/内容在 AI 回答中被引用的情况，输出**可核验**的监测报告与下一步建议。

## 前置条件

- 已绑定工作区与站点。
- 竞品清单、品牌别名、API 凭据由站点补充文件提供（通用标准不含这些）。

## 流程

1. `standards_read('llm-visibility-monitoring')` —— 读"监测"的四类含义、
   爬虫策略、国内外助手与 AI 搜索引擎覆盖清单、可见性维度、内容工程方法。
2. `standards_read('search-engine-integration')` —— 读收录→排名→引用链路，
   确认收录是 AI 引用的前置条件。
3. `monitor_run` —— 执行监测。
4. `monitor_report` —— 取回报告。
5. `search_gsc_stats` / `search_gsc_inspect` —— 交叉核对传统搜索侧数据。
6. `report_write` —— 成文，含结论与下一步动作（刷新 / 退役 / 改稿 / 补推）。
7. 把"需刷新/退役"的结论回灌 `topic-planning`。

## 关键参数

| 参数 | 说明 |
|---|---|
| 监测对象 | 品牌词、产品词、目标关键词 |
| 覆盖渠道 | 国内外 AI 助手 + AI 搜索引擎（清单见标准文档） |
| 时间窗口 | 单次观测须声明窗口，不作趋势结论 |

## 硬性要求

- **单次观测不作趋势结论**，必须声明样本与时间窗口。
- **API 结果与网页表现可能背离**，需分别观测、分别说明。
- 区分相关与因果：引用提升不等于某次改动的直接结果。
- 不臆造竞品数据；竞品清单来自站点补充文件。
- 爬虫策略须按标准核对：哪些必须放行、哪些可限制（分国内外）。

## 示例

```
用户：看看我们品牌在 AI 助手里的可见性怎么样
→ standards_read('llm-visibility-monitoring')
→ monitor_run → monitor_report
→ search_gsc_stats 交叉核对
→ report_write：可见性维度得分 + 异常项 + 下一步（如需刷新哪些文章）
```

## 错误处理

| 现象 | 处理 |
|---|---|
| 监测结果为空 | 确认品牌别名与竞品清单已配置；确认站点已收录 |
| 同名实体混淆 | 用站点补充文件里的品牌别名做消歧 |
| 数据波动大 | 说明样本量与时间窗口，避免趋势化解读 |

## 高风险确认规则

- 基于监测结论批量下线/退役文章：先列出清单并确认。
- 对外发布监测报告（含竞品数据）：确认可公开范围。

## 边界

不撰写、不发布。若瓶颈在稿件质量而非可见性本身，退回 `writing-gate`。
